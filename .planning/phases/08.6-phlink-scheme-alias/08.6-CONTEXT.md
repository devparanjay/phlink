# Phase 8.6 — `phlink://` Scheme Alias — CONTEXT

> Status: LOCKED (auto-mode discuss-phase, 2026-04-29).
> Successor of Phase 4.7's deferred slot 999.4 (see `.planning/phases/04.7-branding-sweep-and-scheme-alias/04.7-CONTEXT.md` D-01).

## Goal

Register `phlink://` as a recognized URL scheme in phlink that resolves to the
same WebUI controllers as `chrome://`, while keeping `chrome://...` working
verbatim as a backwards-compat alias. Surface `phlink://` as the **canonical**
form in the omnibox.

## Requirement traceability

- BRND-02 (PRD §3.6) — phlink-branded WebUI URLs.
- Closes the half of UAT-2026-04-29 that Phase 8.5 left for 8.6 (the
  `chrome://about` page rendering "Chrome URLs" + the chrome-prefixed
  internal URL listing).

## Reference patterns (research, 2026-04-29)

- **Brave** (`brave-browser`, MPL-2.0) — `brave://` is registered via a
  `BraveContentClient::AddAdditionalSchemes` patch that pushes `"brave"` onto
  `schemes->standard_schemes` + `schemes->secure_schemes`, and a
  `BraveContentBrowserClient` override that rewrites `brave://X` → `chrome://X`
  before WebUI lookup. The omnibox display swap is done in a custom
  `LocationBarModelDelegate` rewrite hook.
- **Vivaldi** (`vivaldi://`) — same shape, more invasive (touches
  `OmniboxAutocompleteProvider` directly rather than via the model delegate).
- **Chromium upstream** — `chrome::kChromeUIScheme = "chrome"` is defined in
  `content/public/common/url_constants.h` (header-only constexpr). All standard
  schemes are pushed in `ChromeContentClient::AddAdditionalSchemes` at
  `chrome/common/chrome_content_client.cc:203`.

## Decisions

### D-01 — Alias direction: `chrome://` is the **internal canonical**, `phlink://` is a **display + entry alias**

We do NOT rename the scheme constant `kChromeUIScheme`. Reasons:

- `kChromeUIScheme` appears in ~4,700 sites in the Chromium tree. Renaming the
  constant or its value risks accidental production-build divergence on every
  rebase. Brave learned this the hard way and keeps `chrome` as the internal
  scheme.
- The bookmark/history database serializes URLs as plain strings. If we made
  `phlink` canonical internally, every existing entry would need migration on
  upgrade — out of scope for v0.1.
- Web platform code (CSP, secure-context checks, fetch metadata) compares
  scheme strings; touching them is a known source of fragile breakage.

So: internally everything stays `chrome://`. We add `phlink` as a recognized
**inbound** scheme that gets rewritten to `chrome://` before any URL lookup,
and we add an **outbound** display rewrite so the omnibox shows
`phlink://settings` for the canonical chrome internal URLs.

### D-02 — Phase 8.6 ships **minimum viable** scheme alias

The roadmap success criteria 1–3 are LOCKED for this phase:

1. ✅ `phlink://settings`, `phlink://flags`, `phlink://version`,
   `phlink://about`, `phlink://newtab`, `phlink://components` all load.
2. ✅ `chrome://*` URLs resolve to the same WebUI controllers (alias
   preserved).
3. ✅ Omnibox displays the canonical `phlink://` form when the user types
   either prefix.

The roadmap success criteria 4–5 are SOFT for this phase:

4. 🟡 Internal cross-references emit `phlink://` form — best-effort. Sweep
   `chrome://about` page contents (BRND-04 follow-up) but ANY string baked
   into 3rd-party libs / DevTools URLs / deep settings text is allowed to
   stay `chrome://...` for now.
5. 🟡 Unit tests cover the alias mapping — we ship the
   `tests/branding-audit/runtime-audit.py` extension that adds `phlink://`
   variants of every existing surface; full gtest coverage of the rewrite
   layer is **deferred** to a Phase 8.6.x patchlet if regressions appear.

This bounding is documented up front so we don't expand mid-execute.

### D-03 — Implementation shape (4 patch slots projected → consolidate to 2)

| Slot | Layer | Touchpoint | Patch ID |
|------|-------|-----------|----------|
| (a) | Scheme registration | `chrome/common/chrome_content_client.cc` (push `phlink` onto `standard_schemes` + `secure_schemes`) + new `chrome/common/phlink_url_constants.{h,cc}` defining `kPhlinkUIScheme = "phlink"` | 0117 |

Original plan was 4 patches; consolidating into ONE patch slot **0117** because
each piece is small and they need to land together to avoid build breakage in
the middle. (Same lesson as 8.5: small, atomic, verifiable.)

### D-04 — Use `BrowserURLHandler::AddHandlerPair`, not a new URLLoaderInterceptor

Chromium provides `content::BrowserURLHandler::AddHandlerPair(rewrite_handler,
reverse_handler)` precisely for this case (it's how `about:` → `chrome://`
already works). We register a pair:

- **rewrite**: if URL scheme == `phlink`, replace scheme with `chrome`.
- **reverse** (used by omnibox / display): if URL scheme == `chrome` and host
  is in our WebUI allow-list, replace scheme with `phlink`.

This is the documented hook (see `.refs/chromium/chromium@main/docs/`
`how_cc_works.md` and `BrowserURLHandler` API). Lower risk than a brand-new
URLLoader interceptor and matches the `about:` precedent.

### D-05 — Reverse rewrite is gated on a host allow-list

We do NOT blanket-rewrite every `chrome://X` to `phlink://X` on display. Some
`chrome://` URLs are Chromium-internal in ways we don't want to surface (e.g.
`chrome://internals/...`, `chrome://chrome-urls`, dev-only pages). We allow-list:

- `settings`, `flags`, `version`, `about`, `newtab`, `components`,
  `extensions`, `history`, `bookmarks`, `downloads`, `inspect`, `policy`

Anything else stays `chrome://` for now (BRND-04 follow-up scope creep that
8.6 explicitly does NOT take).

The chrome://about page title fix ("Chrome URLs" → "phlink internal URLs")
is part of this slot per D-02 SC-4.

### D-06 — `phlink://` is a **secure** scheme

Same security posture as `chrome://`:

- Pushed onto `schemes->secure_schemes` (no mixed-content warnings inside
  WebUI pages).
- Standard scheme (URL parsing rules apply).
- NOT savable / NOT extension scheme / NOT referrer scheme — WebUI URLs
  shouldn't appear in any of those contexts.

Site-isolation invariants stay intact because the rewrite happens BEFORE
site assignment — the renderer still sees the URL as `chrome://settings`.

### D-07 — No history dedup

If a user visits `phlink://settings` and then `chrome://settings`, both
appear in history. This is acceptable for v0.1 (and matches Brave's
behavior in early `brave://` builds). Deferred to a future phase if user
feedback says it's confusing.

### D-08 — No omnibox-typed-completion preference

If the user types `chr` the omnibox can autocomplete to `chrome://`; if they
type `phl` it autocompletes to `phlink://`. Both work. We don't bias the
autocomplete in either direction. The `phlink://` form only becomes
canonical at **display time** for already-loaded pages.

### D-09 — Verification: extend `tests/branding-audit/runtime-audit.py`

Add a parallel SURFACES_PHLINK list that tests `phlink://settings`,
`phlink://version`, etc. Both forms must load AND render `phlink` in
`<title>`. Specifically:

- Navigate to `phlink://settings` → expect `document.title` to load
  successfully (not error page) and contain "phlink".
- Navigate to `chrome://settings` → expect omnibox-equivalent display
  string starts with `phlink://`. (Tested by reading
  `chrome.runtime.getManifest()` style? — no; tested by checking
  `Page.frameNavigated` event's URL field returns `chrome://settings`
  internally even though display is rewritten. This is a smoke test
  rather than a strict assertion.)

### D-10 — Out of scope (deferred)

- Migration of existing bookmarks/history entries from `chrome://` to
  `phlink://`. (Lossless: chrome:// still works.)
- Translation strings (Phase 11).
- Per-locale URL aliases (e.g., not needed; URLs are language-neutral).
- Renaming the source-tree constant `kChromeUIScheme`. NEVER.
- Adding `phlink-extension://`, `phlink-search://`, etc. — out of scope.
  Only the user-facing `phlink://` WebUI scheme.
- `chrome-native://` and `chrome-search://` — internal-only, no alias.

## Risks

- **R1**: Site-isolation regression if rewrite happens too late in the
  pipeline. Mitigation: rewrite at `BrowserURLHandler` level (before
  navigation commit), not at renderer side.
- **R2**: Omnibox URL parsing regression — typing `phlink://` could be
  misinterpreted as a search query if the scheme isn't registered as
  standard before the omnibox provider runs. Mitigation: D-06 push to
  `standard_schemes` happens in `AddAdditionalSchemes`, which runs
  before any URL parsing.
- **R3**: Test coverage gap. Mitigation: D-09 runtime audit covers the
  six canonical surfaces; if regression appears, file 8.6.x.
- **R4**: Build break mid-patch — mitigated by single atomic patch slot
  (D-03) and verifying with a full `autoninja chrome` before commit.
