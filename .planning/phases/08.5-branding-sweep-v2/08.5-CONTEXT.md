> **Provenance:** Phase 4.7 ran a strings-only audit of the linked binary, classified 188 hits into 8 categories, and concluded "no genuinely user-visible Chromium strings remain (all covered by Phase 3 BRANDING + IDS_PRODUCT_NAME)." UAT of Phase 8 (`chrome://settings/appearance`, 2026-04-29) **falsified** that conclusion: window title, About box, version page, settings header, and several menu items render "Chromium" / "Chrome" / "Google Chrome" verbatim. The 4.7 allowlist was over-permissive — strings appearing in `.grd` files but rendering at runtime were waved through as "non-user-visible".

## 1. Goal restated

Eliminate the **rendered-UI** Chromium identity strings that survive into Phase 8's UAT. Re-classify the 4.7 allowlist using runtime evidence (not just static analysis), patch the user-visible surfaces, lock the macOS bundle metadata to `phlink`, and add a regression gate that runs against a launched browser — not just `strings(1)` over the binary.

## 2. Hard constraint review

## 3. Domain & boundaries

**In scope (Phase 8.5):**
- Re-classification of `tests/branding-audit/allowlist.txt` using runtime evidence (CDP-driven page-title + DOM grep against the launched binary).
- GRD-string patches for the rendered surfaces enumerated in §6.
- macOS `Info.plist` `CFBundleName` / `CFBundleDisplayName` / `CFBundleExecutable` lock to `phlink` (chromium-src `chrome/app/app-Info.plist` template + `build/mac/tweak_info_plist.py`).
- New CI gate `tests/branding-audit/runtime-audit.py` — CDP-driven smoke that visits `chrome://settings`, `chrome://settings/appearance`, `chrome://version`, `chrome://flags`, `chrome://about`, the New Tab Page, and the About dialog (via `chrome://settings/help`), and asserts no `\b(Chromium|Google Chrome|Chrome)\b` matches in `document.title` or in a curated set of selectors (settings header, About box, version page).
- Wire the new runtime audit into `.github/workflows/lint.yml` behind a `PHLINK_BINARY` env gate (same pattern as `tests/benchmark_60tab/` — skips cleanly when binary is absent).

**Out of scope (deferred):**
- `phlink://` scheme registration → **Phase 8.6**.
- DevTools UI strings (`Chrome DevTools` etc.) — DevTools surface targets developers, lower priority; defer to a future Phase 8.7 if user-visibility complaints arise.
- Error-page boilerplate (`chrome-error://`) — internal, rarely seen, defer.
- Localization beyond `en-US.pak` — phlink ships English-only at v1; other locale `.grd` files inherit via fallback. We patch the `_strings.grd` master, not 50× per-locale.
- `chrome://flags` *flag descriptions* (deep upstream Chrome-feature copy) — out of scope; only the page chrome (title, header) gets renamed.
- Updater / installer strings (`Google Chrome Updater`) — Phase 10 (installers) territory.

## 6. Decisions

### D-01 — Sweep target list comes from runtime evidence, not static grep

The Phase 8.5 work list is **derived empirically** by launching the current build and capturing every visible Chromium/Chrome/Google-Chrome string across the canonical URLs in §3 (in scope). The DISCUSSION-LOG records the captured list verbatim; the planner converts it into per-string patch tasks.

**Rationale.** Phase 4.7 failed because it inferred user-visibility from `.grd` filename / element type. The only reliable way to know if a string is user-visible is to see it rendered. CDP `Page.getNavigationHistory` + `Runtime.evaluate('document.title')` + a tight set of `document.querySelector` reads gives ground truth.

### D-02 — Patch the master `.grd` files, not per-locale `.xtb` translations

phlink ships English-only at v1 (PRD §11). Master `.grd` patches propagate to `en-US.pak`. Per-locale `.xtb` translation files are upstream-controlled and would create a 50-file rebase nightmare each Chromium stable bump.

**Rationale.** Cost / benefit: patching `.xtb` for languages we don't ship is pure rebase tax. Defer to whichever Phase introduces locales.

### D-03 — Two patch slots: `0116` (Info.plist) + `0117` (GRD strings)

Split because they touch disjoint subtrees and have different test gates: Info.plist is verified by `defaults read`, GRD strings by the new runtime audit. Smaller patches = cleaner rebase.

**Rationale.** Phase 8 split worked well at 5 patches (`0110`–`0114`); maintain that discipline.

### D-04 — Regression gate is *runtime CDP*, with strings-audit kept as a fast pre-flight

`tests/branding-audit/audit.sh` (existing, ~1s) stays as the cheap canary. New `tests/branding-audit/runtime-audit.py` (CDP, ~30s with binary launch) runs in CI when `PHLINK_BINARY` is set, and locally when the dev runs it explicitly. Both must pass before merge for any patch in this phase.

**Rationale.** Defense-in-depth. Static catches regressions to `.grd` master files; runtime catches anything that slips through (e.g., a TS file that hardcodes "Chromium").

### D-05 — `CFBundleName` / `CFBundleDisplayName` / `CFBundleExecutable` all set to `phlink`

Macos bundle uses three identity fields. All three move to `phlink`; `CFBundleIdentifier` stays at `org.phlink.phlink` (already set Phase 3). `LSApplicationCategoryType`, `CFBundleVersion` etc. unchanged.

**Rationale.** Finder Get-Info, `defaults read`, `lsregister`, and screenshot OCR all read these fields. Setting only one leaves the other two as silent regressions.

### D-06 — Severity classification for sweep targets

Each captured string is tagged `block` / `nice-to-have` / `defer-to-8.7`:
- `block`: window title, About dialog, settings page header, version page header, omnibox placeholder text. **Must ship in 8.5.**
- `nice-to-have`: tooltip strings, menu-bar items, second-tier dialog headers. Ship in 8.5 if cheap; defer otherwise.
- `defer-to-8.7`: DevTools UI, error pages, internal `chrome://histograms` etc.

**Rationale.** Without triage, sweep balloons. UAT surfaced ~5–10 first-tier surfaces; full-bundle GRD audit would surface hundreds. We ship the visible win.

### D-07 — Allowlist re-classification preserves audit history

`tests/branding-audit/allowlist.txt` gains a `## rendered-ui-must-patch` section above the existing categories. Entries promoted out of the 8 inert categories into the new section keep their original line context as a comment so future sweeps can audit the chain of decisions.

**Rationale.** Self-documenting forensic trail. If a later UAT challenges 8.5's classifications too, the next sweeper sees the history.

### D-08 — Runtime audit harness language: Python + websockets

Same stack as `tests/benchmark_60tab/` and `tests/network-capture/`. No Node toolchain. CDP via raw websocket (lightweight; the harness only needs `Page.navigate` + `Runtime.evaluate`).

**Rationale.** Consistency with existing test infra. Pytest collection picks it up automatically; CI already has Python ≥ 3.11.

### D-09 — Allowlist for legitimate "Chrome" strings (e.g., Chrome Web Store)

The phrase "Chrome Web Store" stays — it's a proper noun referring to Google's actual store, which phlink reuses (PRD locked decision: extension store reuses Chrome Web Store URLs). Same for "Chrome OS" if it appears in any UA-string fallback. Runtime-audit harness exempts these via a small allowlist of literal phrases.

**Rationale.** Renaming Google's product breaks user expectations and creates fraud-vector ambiguity ("phlink Web Store" implies phlink-curated; the actual store is Google's).

### D-10 — Don't touch `chrome://` URL strings in 8.5

Any "go to chrome://settings" copy stays for now. Phase 8.6 introduces the `phlink://` alias and rewrites those copy references in the same pass. Doing it twice creates wasted patches.

**Rationale.** Sequencing — keep 8.5 string-only, 8.6 scheme-only, audit at the boundary.
