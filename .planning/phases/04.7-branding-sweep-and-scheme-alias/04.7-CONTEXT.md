# Phase 4.7 — Branding Sweep + `phlink://` scheme alias — CONTEXT

> Sourced from upstream Chromium under `/Volumes/Tools/dev/chromium-src/src/`, prior phlink patches (0001–0012), PRD §3.6 (locked branding posture), and the post-build audit on 2026-04-29 (HEAD `9457df2` + the AIM follow-up at `47d702e`).

## Phase Goal (from ROADMAP)

Eliminate the remaining user-visible "Chromium" / "Google Chrome" strings, expose phlink-branded WebUI URLs as `phlink://...`, and keep `chrome://` working as a backwards-compat alias so existing developer muscle memory and bookmarks keep resolving.

## Requirements covered

`BRND-01` (no Chromium/Google Chrome branding in shipping binaries — PRD §3.6),
`BRND-02` (phlink-branded scheme — PRD §3.6).

## Decisions

### D-01 — Two-tier scope: cosmetic sweep is in; scheme alias is **deferred**

Phase 4.7 originally proposed both (a) a GRD branding sweep and (b) a `chrome://` → `phlink://` scheme alias. After auditing the cost vs. value:

- **(a) GRD branding sweep** — IN SCOPE. Phase 3 already substituted the high-traffic strings (BRANDING file, IDS_PRODUCT_NAME, IDS_PRODUCT_DESCRIPTION). The residue is in long-tail GRD strings (settings page subtitles, about-box copy referencing "Chromium", flag descriptions, error pages). Tractable in a single pass; mostly mechanical.

- **(b) `phlink://` scheme alias** — DEFERRED to a dedicated phase (placeholder slot **999.4**, see ROADMAP backlog). Reasons:
  1. `chrome://` is wired through ~thousand call sites: `content/public/common/url_constants.cc` (`kChromeUIScheme`), `ContentClient::AddSchemes`, `ChromeContentBrowserClient::GetAdditionalWebUISchemes`, `WebUIControllerFactory`, the omnibox URL formatter, every `*_browsertest.cc` that hardcodes `chrome://...`. Touching all of those for cosmetic gain is the wrong trade in v1.
  2. `chrome://` URLs are a developer/power-user surface — day-1 phlink users do not see them.
  3. PRD §3.6 (BRND-02) is satisfied by *displaying* `phlink://...` in the omnibox bar; the underlying scheme can stay `chrome` for now. We do that cosmetic display rewrite in a future phase, alongside a proper scheme registration that ships with full test coverage.

This decision is recorded so a future contributor doesn't re-litigate it inside the planner.

### D-02 — Audit-first, patch-second

We do **not** start writing patches blind. The first plan in this phase is a structured audit that produces a kill-list of every remaining user-visible "Chromium" / "Google Chrome" / "chromium" string in the built bundle. Inputs:

- `strings phlink.app/Contents/MacOS/phlink | grep -iE 'chromium|google chrome'`
- `grep -rE '(Chromium|Google Chrome)' chrome/app/*.grd chrome/app/resources/` (limited to the ~30 GRD files referenced by `chrome/app/generated_resources.grd`).
- Manual smoke: open about box, settings landing, flags page, version page, app menu — note every visible occurrence.

Output: a kill-list with `(location, current_string, replacement)` rows that drives plans 04.7-02..04.7-04.

### D-03 — Replacement strings are derived from `IDS_PRODUCT_NAME`, not hardcoded

Where a Chromium GRD string says "Chromium" and a `IDS_PRODUCT_NAME` placeholder is already in scope (or could be added), we use the placeholder. We only hardcode "phlink" when the surrounding sentence cannot accept a `<ph name="PRODUCT_NAME">` substitution without retranslation churn. Hardcoding "phlink" in English-only strings is acceptable for v1 alpha (PRD §3.6 footnote: localization is a Phase 11 concern).

### D-04 — Patches stay in slot range 0013–0029

Phase 3 reserved 0001–0099 for branding patches; 0001–0006 are taken; 0007–0012 are Phase 4.6 telemetry plugs in the same root subtree. We use **0013–0029** for Phase 4.7 branding sweep patches. If we exceed 0029, we re-evaluate the slot allocation in `patches/README.md`.

### D-05 — Verification: built-binary string scan + manual smoke

Verification gate for the phase:

1. `strings phlink.app/Contents/MacOS/phlink | grep -iE 'chromium|google chrome'` returns only entries on an explicit allow-list (e.g., copyright headers in third-party code, `chromium.googlesource.com` URLs in code-comment payloads inside resources, the BRANDING file's `MAC_CREATOR_CODE`-adjacent build metadata). The allow-list lives in `tests/branding-audit/allowlist.txt`.
2. About box, settings landing page, app menu, version page screenshots show no "Chromium" or "Google Chrome".
3. `tests/network-capture/` still passes (regression gate).
4. Smoke test: `phlink --version` prints "phlink ..." (regression of Phase 3).

Plan 04.7-05 builds the `tests/branding-audit/` harness so this is repeatable on every rebuild.

### D-06 — Out of scope (explicitly)

- `phlink://` scheme registration (deferred — see D-01).
- Changing the macOS bundle identifier away from `org.phlink.phlink` (already set in Phase 3).
- Renaming Chromium-internal C++ symbols (`kChromeUIScheme`, `chrome::` namespace, etc.) — these are not user-visible.
- Translating non-English locales — Phase 11.
- Replacing the Chromium logo / Bug icon assets with phlink iconography — that is its own design phase (placeholder slot **999.5** for "phlink visual identity").
